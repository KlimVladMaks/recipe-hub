# ЛР2: Реализация микросервисов

## Задача

Опираясь на документ, сформированный в рамках ДЗ4, реализовать разделение монолитного бэкенд-приложения на микросервисы: API Gateway, User Service и Recipe Service.

## Ход работы

### 1. Анализ существующей структуры

На момент начала работы в директории `services/` уже были частично созданы файлы микросервисов, но многие эндпоинты отсутствовали. Полный список эндпоинтов был взят из legacy-монолита (`legacy-monolith/`).

### 2. User Service — добавление недостающих эндпоинтов

#### 2.1 User CRUD

Созданы файлы:

- **`src/routes/user.routes.ts`** — маршруты для управления пользователями:
  - `GET /users` — список пользователей (только для админа)
  - `GET /users/me` — профиль текущего пользователя
  - `PATCH /users/me` — обновление своего профиля
  - `DELETE /users/me` — удаление своего аккаунта
  - `GET /users/:userId` — получение пользователя по ID
  - `DELETE /users/:userId` — удаление пользователя (админ)
  - `PATCH /users/:userId/role` — изменение роли (админ)

- **`src/controllers/user.controller.ts`** — контроллер с обработкой запросов и проверкой прав доступа

- **`src/services/user.service.ts`** — сервис с бизнес-логикой:
  - `getUsers(page, limit)` — пагинированный список
  - `getUser(userId)` — получение по ID
  - `updateUser(userId, data)` — обновление профиля
  - `deleteUser(userId)` — удаление пользователя
  - `updateUserRole(userId, data)` — изменение роли

- **`src/schemas/user.schemas.ts`** — добавлены схемы валидации:
  - `UserUpdateSchema` — опциональные поля для обновления
  - `UserRoleUpdateSchema` — поле role
  - `UserReadListSchema` — массив пользователей

#### 2.2 Subscription CRUD

Созданы файлы:

- **`src/routes/subscription.routes.ts`** — маршруты для подписок:
  - `GET /users/me/subscriptions` — мои подписки
  - `GET /users/me/subscribers` — мои подписчики
  - `GET /users/:userId/subscribe` — проверка подписки
  - `POST /users/:userId/subscribe` — подписаться
  - `DELETE /users/:userId/subscribe` — отписаться
  - `GET /users/:userId/subscriptions` — подписки пользователя
  - `GET /users/:userId/subscribers` — подписчики пользователя

- **`src/controllers/subscription.controller.ts`** — контроллер подписок

- **`src/services/subscription.service.ts`** — сервис подписок:
  - `getSubscriptions(userId, page, limit)`
  - `getSubscribers(userId, page, limit)`
  - `getSubscriptionUserIds(userId)` — для feed (только ID)
  - `isSubscribed(currentUserId, userId)`
  - `subscribe(currentUserId, userId)`
  - `unsubscribe(currentUserId, userId)`

- **`src/schemas/subscription.schema.ts`** — схема `IsSubscribedToUserReadSchema`

#### 2.3 Внутренние эндпоинты

Создан **`src/routes/internal.routes.ts`** — эндпоинты для межсервисного взаимодействия (без JWT-аутентификации):
- `GET /internal/users/:userId` — данные пользователя
- `GET /internal/users/:userId/is-admin` — проверка админа
- `GET /internal/users/batch?ids=1,2,3` — массовое получение
- `GET /internal/users/:userId/subscription-ids` — ID подписок (для feed)

#### 2.4 Модификация существующих файлов

- **`src/routes/index.ts`** — подключены новые роутеры
- **`src/services/auth.service.ts`** — добавлен метод `isUserAdmin()`

### 4. API Gateway — обновление маршрутизации

#### 4.1 Прокси для новых маршрутов

В **`src/routes/index.ts`** добавлены прокси для:
- Комментариев: `/recipes/:recipeId/comments`
- Шагов: `/recipes/:recipeId/steps`
- Рейтингов: `/recipes/:recipeId/rating`
- Сохранений: `/recipes/:recipeId/save`
- Подписок: `/users/me/subscriptions`, `/users/:userId/subscribe` и др.

#### 4.2 Композиция для feed

Создан **`src/routes/feed.ts`**:
1. Получает `currentUserId` из заголовка `x-user-id` (установлен authMiddleware)
2. Запрашивает user-service: `GET /internal/users/{currentUserId}/subscription-ids`
3. Запрашивает recipe-service: `GET /internal/recipes/by-authors?authorIds=...`
4. Возвращает объединённый результат

#### 4.3 Исправление порядка маршрутов

В процессе тестирования обнаружено, что общий прокси `/users` перехватывал запросы к `/users/me/feed` и `/users/me/subscriptions`. Исправлено перемещением специфичных маршрутов **до** общего прокси.

### 5. Межсервисное взаимодействие

#### 5.1 HTTP (синхронное)

Recipe Service → User Service:
- При получении рецепта: запрос `GET /internal/users/:authorId`
- При получении комментария: запрос `GET /internal/users/:userId`
- При проверке прав: запрос `GET /internal/users/:userId/is-admin`
- При массовом получении: запрос `GET /internal/users/batch?ids=...`

#### 5.2 RabbitMQ (асинхронное)

User Service публикует события:
- `user.created` — при регистрации
- `user.deleted` — при удалении

Recipe Service потребляет:
- `user.deleted` — каскадное удаление всех данных пользователя

### 6. Схемы баз данных (Prisma)

**User Service (`prisma/schema.prisma`):**
```prisma
model User {
  id        Int    @id @default(autoincrement())
  username  String @unique
  password  String
  firstName String
  lastName  String
  about     String?
  role      String @default("user")
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  subscriptions       Subscription[] @relation("subscriptions")
  subscribedTo        Subscription[] @relation("subscribedTo")
}

model Subscription {
  id           Int      @id @default(autoincrement())
  subscriberId Int
  subscribedToId Int
  createdAt    DateTime @default(now())

  subscriber  User @relation("subscriptions", fields: [subscriberId], references: [id])
  subscribedTo User @relation("subscribedTo", fields: [subscribedToId], references: [id])

  @@unique([subscriberId, subscribedToId])
}
```

**Recipe Service (`prisma/schema.prisma`):**
```prisma
model Recipe {
  id          Int       @id @default(autoincrement())
  authorId    Int
  title       String
  description String?
  difficulty  Difficulty?
  isPublished Boolean   @default(false)

  updatedAt   DateTime  @updatedAt

  recipeDishTypes   RecipeDishType[]
  savedBy           SavedRecipe[]
  comments          Comment[]
  recipeIngredients RecipeIngredient[]
  ratings           RecipeRating[]
  steps             RecipeStep[]
  media             RecipeMedia[]
}

// ... остальные модели: RecipeMedia, DishType, RecipeDishType,
//     Ingredient, RecipeIngredient, RecipeStep, RecipeStepMedia,
//     SavedRecipe, Comment, CommentLike, RecipeRating
```

## Вывод

В результате работы монолитное приложение было разделено на три микросервиса: API Gateway (порт 3000), User Service (порт 3001) и Recipe Service (порт 3002). Каждый микросервис имеет собственную базу данных (database-per-service) и собственную бизнес-логику. Все эндпониты из legacy-монолита имеют соответствие в микросервисах. Межсервисное взаимодействие реализовано через HTTP (синхронные запросы данных пользователей) и RabbitMQ (асинхронные события). API Gateway обеспечивает единую точку входа с JWT-аутентификацией и композицией данных для ленты подписок.
