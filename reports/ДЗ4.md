# ДЗ4: Технический дизайн микросервисной архитектуры

## Задача

Разделить монолитное бэкенд-приложение (платформа для обмена рецептами и кулинарный блог) на микросервисы, придерживаясь концепции database-per-service. Спроектировать микросервисную архитектуру: определить взаимосвязи между микросервисами, способы их взаимодействия, разделение базы данных, а также описать эндпоинты для межсервисного взаимодействия.

## Ход работы

### 1. Анализ монолитного приложения

Исходное монолитное приложение (`legacy-monolith/`) построено на стеке:
- **Express.js** — веб-фреймворк
- **PostgreSQL** — база данных
- **Prisma ORM** — работа с БД
- **JWT** — аутентификация

**Сущности монолита:**
- `User` — пользователи (id, username, password, firstName, lastName, about, role)
- `Recipe` — рецепты (id, authorId, title, description, difficulty, isPublished)
- `RecipeMedia` — медиафайлы рецепта
- `RecipeStep` — шаги приготовления
- `RecipeStepMedia` — медиафайлы шагов
- `DishType` — типы блюд
- `RecipeDishType` — связь рецептов с типами блюд
- `Ingredient` — ингредиенты
- `RecipeIngredient` — связь рецептов с ингредиентами
- `Comment` — комментарии
- `CommentLike` — лайки комментариев
- `SavedRecipe` — сохранённые рецепты
- `RecipeRating` — рейтинги рецептов
- `Subscription` — подписки пользователей

### 2. Проектирование микросервисной архитектуры

#### 2.1 Выделение микросервисов

На основе анализа предметной области выделены три микросервиса:

| Микросервис | Порт | Ответственность |
|-------------|------|-----------------|
| **API Gateway** | `:3000` | Аутентификация (JWT), маршрутизация, композиция (feed) |
| **User Service** | `:3001` | Пользователи, подписки, аутентификация |
| **Recipe Service** | `:3002` | Рецепты, комментарии, шаги, рейтинги, справочники |

#### 2.2 Database-per-service

Каждый микросервис имеет собственную базу данных PostgreSQL:

**user-db (`:5433`) — таблицы:**
- `users` — пользователи
- `subscriptions` — подписки

**recipe-db (`:5434`) — таблицы:**
- `recipes` — рецепты
- `recipe_media` — медиафайлы рецептов
- `recipe_steps` — шаги приготовления
- `recipe_step_media` — медиафайлы шагов
- `dish_types` — типы блюд
- `recipe_dish_types` — связь рецептов с типами блюд
- `ingredients` — ингредиенты
- `recipe_ingredients` — связь рецептов с ингредиентами
- `comments` — комментарии
- `comment_likes` — лайки комментариев
- `saved_recipes` — сохранённые рецепты
- `recipe_ratings` — рейтинги рецептов

### 3. Межсервисное взаимодействие

#### 3.1 HTTP (синхронное взаимодействие)

**Recipe Service → User Service (внутренние HTTP-запросы):**

Recipe Service не имеет своей таблицы `users`, поэтому для получения данных о пользователях (авторах рецептов, комментаторов) он обращается к User Service через внутренние эндпоинты.

| Метод | Эндпоинт | Описание | Ответ |
|-------|----------|----------|-------|
| GET | `/internal/users/:userId` | Получить пользователя по ID | `{ id, username, firstName, lastName, about, role, createdAt, updatedAt }` |
| GET | `/internal/users/:userId/is-admin` | Проверить роль администратора | `{ isAdmin: boolean }` |
| GET | `/internal/users/batch?ids=1,2,3` | Получить нескольких пользователей | `[{ id, username, ... }]` |
| GET | `/internal/users/:userId/subscription-ids` | Получить ID подписок (для feed) | `{ authorIds: [1, 2, 3] }` |

**Recipe Service (внутренние эндпоинты для feed):**

| Метод | Эндпоинт | Описание | Ответ |
|-------|----------|----------|-------|
| GET | `/internal/recipes/by-authors?authorIds=1,2,3&page=1&limit=20` | Получить рецепты по списку авторов | `[{ id, title, ... }]` |

#### 3.2 RabbitMQ (асинхронное взаимодействие)

**User Service → RabbitMQ → Recipe Service**

User Service публикует события в RabbitMQ (exchange: `user-exchange`, routing key: `user.*`):

| Событие | Когда отправляется | Данные |
|---------|-------------------|--------|
| `user.created` | При регистрации нового пользователя | `{ userId, username }` |
| `user.deleted` | При удалении пользователя | `{ userId }` |

Recipe Service потребляет эти события:
- При получении `user.deleted` — каскадно удаляет все рецепты, комментарии, лайки, рейтинги и сохранения этого пользователя.

#### 3.3 API Gateway (композиция)

**Feed (GET `/users/me/feed`):**
1. API Gateway получает `currentUserId` из JWT-токена (через `authMiddleware`)
2. Делает запрос в User Service: `GET /internal/users/{currentUserId}/subscription-ids`
3. Получает список ID авторов, на которых подписан пользователь
4. Делает запрос в Recipe Service: `GET /internal/recipes/by-authors?authorIds=...`
5. Возвращает объединённый результат клиенту

### 6. Аутентификация и безопасность

1. **API Gateway** проверяет JWT-токен во всех защищённых маршрутах
2. После верификации токена Gateway добавляет заголовки:
   - `x-user-id` — ID пользователя
   - `x-user-role` — роль пользователя
3. Микросервисы доверяют этим заголовкам (внутренняя сеть Docker)
4. Внутренние эндпоинты (`/internal/*`) не имеют JWT-аутентификации, так как доступны только внутри Docker-сети

## Вывод

В результате проектирования была разработана микросервисная архитектура для платформы обмена рецептами, состоящая из трёх сервисов: API Gateway, User Service и Recipe Service. Каждый сервис имеет собственную базу данных (database-per-service). Межсервисное взаимодействие реализовано двумя способами: синхронное HTTP-взаимодействие (Recipe Service запрашивает данные пользователей у User Service) и асинхронное через RabbitMQ (события создания/удаления пользователя). API Gateway выполняет роль единой точки входа, обеспечивая JWT-аутентификацию, маршрутизацию и композицию данных для ленты подписок (feed). Все эндпоинты описаны с указанием методов, путей, middleware и форматов ответов.
